# Developer 1 prep memo: the codebase, and what it can still do for us (2026-11-26)

## 1. Health verdict: well tested, badly overgrown (5/10)

**Good**
- **2,095 tests pass in 18 seconds** (run offline today, no credentials present).
- Defects are documented with evidence (e.g. headers of `tools/pit_fetch.py`, `tools/pit_pool.py`).
- The MEXC client (`futuresbot/marketdata.py`) is mature: retries, unanswered-order recovery, key-expiry detection.

**Bad**
- **One class does everything.** `futuresbot/runtime.py` is 15,361 lines, almost all of it one class (`FuturesRuntime`) with ~383 methods. `_enter_trade` alone is ~690 lines.
- **Far too many settings.** The code reads **~866 distinct environment-variable names** (my count of `env_*`/`os.getenv` calls). Railway has 199 set, and only about 30 change behaviour (`docs/LIVE_CONFIG.md`).
- **Switched-off code is still running code.** 60 of 73 modules (~34k lines) load at start-up (my import-graph count from `main.py`). Live trading today is one mode (random-tick WILDCARD, trial 27, `futuresbot/random_mode.py`), but the old PMT exit function `_pmt_hard_exit` still manages every live position.
- **Several "tidy-up" flags would cause harm** (`docs/LIVE_CONFIG.md` §6). Clearing `FUTURES_STRATEGY_MODE` or `FUTURES_WILDCARD_CONVEX_EXIT_ENABLED` would silently change live exits.
- **Sprawl.** `docs/DECISION_RULE.md` is 19,787 lines; `README.md` is out of date; `tools/` holds 129 scripts (~31k lines), 65 of them meant to run via `railway run`.
- **The evidence lives only on the owner's laptop**: a year of 15m bars for 622 symbols, the 1m bars, and the `wc/` study folders cited 167 times (`DECISION_RULE.md` ~17839, `tools/archive_evidence.py`). None of it is in the repo, and the archive job has been down since about 10-21.

**Changing it safely:** small changes are safe (tests plus the release gate catch regressions). Structural changes are slow and risky because live exits are tangled with legacy code.

## 2. Approach 2: what we already have

Most of the hard parts already exist and were graded against live trades:

| Need | Existing asset | Status |
|---|---|---|
| Candidate list at each tick | `random_mode.universe / wildcard_row / rank`, `wildcard.detect_wildcard_signal` | Pure functions with no input/output, port of the backtest |
| Point-in-time universe (no hindsight) | `tools/pit_pool.py` | Fixes the "today's majors" bias |
| Data fetch that refuses gaps | `tools/pit_fetch.py`, `futuresbot/replay/bars.py` | bars.py supports only Min1/Min15 |
| One exit engine, FAIR-price | `futuresbot/replay/exits.py` (`resolve_exit`, `bar_seconds` argument) | On live entries: **corr 0.999, 93.5% within 0.1R** (`DECISION_RULE.md` ~17845) |
| Sizing like live | `futuresbot/replay/sizing.py` | 148/151 fills within 5% |
| Replay-vs-live grader | `futuresbot/replay/acceptance.py`, `tools/replay_vs_live.py` | Expects Railway feature-store files |
| Luck controls | `tools/pit_placebo.py`, `tools/mc_ledger.py`, `a1/analyze.py` | Permutation and time-shift placebo |

**New fact checked today (public data):** MEXC still serves **5-minute LAST and FAIR bars back to at least 2026-05-10**. 1-minute bars only go back about 30 days (to about 10-28). So the whole exploration window (08-28 to 10-19) can be replayed on 5m fair-price bars **without Railway or the laptop**.

**Known weak spots**
- WILDCARD *entry* replay passed only "marginally", and only once live's recorded refusals were applied. Without them, recall was 0.72 and precision 0.60 (`DECISION_RULE.md` ~17849).
- The exploration window mixes trial designs: detector-based trading before trial 24, random-tick after.
- Delisted coins are missing from the public symbol list (survivorship). How many are missing is unknown.
- Exits on 5m bars will be less exact than on 1m. This has to be re-measured on the real trades.

**Approach 1 scripts** (`scratchpad/a1/build_features.py`, `analyze.py`) are reusable as the feature builder and luck benchmark, after fixes:
1. `get()` silently returns `{}` after 4 failures and the cache then keeps a short file forever (the defect `pit_fetch.py` exists to stop).
2. Lookbacks are fuzzy by up to 1 hour, and token and BTC returns use different offsets.
3. Features come from 1h bars only.
This would not change Approach 1's conclusions much, but matters at thousands of candidates.

**Approach 2 plan and effort: about 5 developer-days (range 4-7)**
1. Add Min5 to `bars.py` and fetch 5m FAIR/LAST bars for the universe: 0.5-1 day (mostly fetch time).
2. Build the candidate generator. Every 6h tick (or every scan) from 08-28, point-in-time universe, both sides: 1 day.
3. Apply one fixed exit rule with `resolve_exit(bar_seconds=300)` plus fees and funding: 0.5-1 day.
4. Validate against the 235 real exploration trades: exits on real entries first, then entry matching: 1 day. **Go/no-go: if exits on real entries do not correlate at 0.9 or above, stop.**
5. Generalise `build_features.py` to candidates and test leads 1-3 with the permutation and placebo controls: 1 day.
6. One final run on the locked holdout, plus a write-up: 0.5 day.

Optional +1 day: if the owner pulls the laptop archive, we get live-recorded candidates for 09-23 to 10-21.

## 3. Simplifying the bot

- **Strip in place** (delete the PMT/sniper/squeeze/breakaway paths and dead flags, split `runtime.py`): **12-20 days**. High risk, because live exits run through the legacy code. The test suite makes it possible.
- **New minimal executor** (~2k lines, reusing the MEXC client and replay engines): **8-12 days**, plus 2-4 weeks of shadow running before real money.
- **My advice:** do neither until something shows an edge. Simplification earns no money on its own.

## 4. Reusing components in a new project

Worth keeping: the MEXC client; `replay/bars.py`, `exits.py`, `sizing.py`, `acceptance.py`; `pit_fetch.py`, `pit_pool.py`, `pit_placebo.py`, `mc_ledger.py`; the Approach 1 feature builder; the `archive_evidence.py` pattern (save data before the exchange deletes it); the shadow-ledger idea (record what you did not trade); pre-registration.

Effort:
- **3-5 days** to turn these into a standalone "research kit" with no Railway dependency. That includes cutting `replay/exits.py`'s import of `FuturesRuntime`.
- **+2-4 days** per new exchange or broker adapter. Effort is unknown for non-crypto brokers until we pick one. Whether we can legally use them from the UK is the Architect's call.

## My position for the meeting

In parallel, extract the research kit, which is the real value of the last seven months.
